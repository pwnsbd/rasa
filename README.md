# Rasa

Local-first, GPU-aware desktop app for extracting the visual style of a reference image (an **Essence**) and reapplying it to other photos. See [`docs/rasa-product-spec.md`](docs/rasa-product-spec.md) for the full product/technical spec.

Architecture follows the same Electron + Python-sidecar pattern as the sibling `pdfToAudio` project: a React/Vite/TypeScript renderer talks to a local-only FastAPI sidecar (spawned by Electron's main process) that owns all model inference and stays off any network beyond `127.0.0.1`.

## Layout

```
electron/       Electron main process + preload (window, IPC, sidecar lifecycle)
ui/             React + Vite + TypeScript renderer
sidecar/        Python FastAPI backend — device detection, (soon) the extraction/generation pipeline
scripts/        Dev tooling (sidecar venv + torch setup)
docs/           Spec and architecture notes
```

## Setup

```
npm install
npm run sidecar:setup   # creates sidecar/venv, installs deps + the right torch build
npm run dev              # Vite dev server + Electron, concurrently
```

`sidecar:setup` detects an NVIDIA GPU via `nvidia-smi` and installs a CUDA (cu128) torch build if found, CPU otherwise. cu128 specifically (not an older CUDA build) is required for current-gen "Blackwell" GPUs (RTX 50-series, compute capability sm_120, including this project's RTX 5070 dev target) — see the comment in [`scripts/setup-sidecar.js`](scripts/setup-sidecar.js).

All app data — models (~13GB+ once the subject-isolation dependencies' own model downloads are included), Essences, Media, cache, db, and Electron's own internal caches — lives in `<project-root>/appdata/` **in dev only**, not wherever Electron's OS-default `userData` would otherwise put it (usually the C: drive on Windows, `%APPDATA%\rasa`). This is a deliberate `app.setPath('userData', ...)` in `electron/main.js`, gated on `!app.isPackaged` — not a default worth trusting an env var to redirect every launch — that was tried first, and a forgotten env var on one real run silently re-downloaded the entire model cache back onto C:. `RASA_MODELS_DIR` still exists as a further override if you want the model cache specifically somewhere other than `appdata/models` (everything else stays under `appdata/`). A **packaged** install does not redirect `userData` at all — see Packaging/shipping below for why.

Device status (GPU name, CUDA availability, compute capability, VRAM, torch version) is visible in-app on the Settings screen, and always available at `GET http://127.0.0.1:8843/health` while the sidecar is up.

## Packaging/shipping

First real pass at "can this be installed by someone who isn't a developer," scoped deliberately to Windows + GPU-owning users (matches everything actually built/tested this project) with a free/open-source distribution model.

**Licensing**: every model Rasa depends on allows commercial distribution — verified per-model, not assumed, in [THIRD_PARTY_LICENSES.md](THIRD_PARTY_LICENSES.md). One real trap avoided rather than hit: Depth Anything V2's Base/Large/Giant checkpoints are non-commercial (CC-BY-NC-4.0); `sidecar/depth.py` was already pinned to the Apache-2.0 Small checkpoint before this was checked, for size/speed reasons that turned out to also be the licensing-correct choice. Rasa's own code is MIT ([LICENSE](LICENSE)).

**The sidecar-without-Python problem**: `sidecar/venv` (what dev uses) assumes a system Python + `npm run sidecar:setup` run by a developer — not something to ask an end user to do. A packaged install instead bundles Python's official Windows *embeddable* distribution (~16MB, fetched by [`scripts/fetch-embed-python.js`](scripts/fetch-embed-python.js) — not committed to git, run via `npm run dist:prep`) as `extraResources`, and [`electron/sidecarBootstrap.js`](electron/sidecarBootstrap.js) copies it into a writable per-user location on first launch, then `pip install`s `sidecar/requirements.txt` + the right torch build (same CUDA-detection logic as `setup-sidecar.js`, reused) — all before the sidecar process itself ever starts. [`FirstRunOverlay.tsx`](ui/src/components/FirstRunOverlay.tsx) shows this progress instead of leaving the window looking frozen; it never appears in dev. Every piece of this — extraction, the embeddable distribution's `._pth` site-packages patch, pip bootstrap, a real `pip install`, and the full packaged app's `files`/`extraResources` resolving correctly (confirmed via `npx electron-builder --dir`, inspecting the resulting `resources/` layout directly) — was run for real while building it, not just written and assumed to work.

`npm run dist` builds the UI, fetches the embeddable Python if not already present, and produces a Windows NSIS installer (per-user install — `perMachine: false` — so it never needs admin rights, consistent with the userData fix above).

**App icon**: [`scripts/make-icon.py`](scripts/make-icon.py) generates `electron/icon.ico`/`icon.png` — a stylized distillation flask matching the existing in-app visual language (same silhouette family as `DistillationBottle.tsx`, same charcoal/gold palette as `tailwind.config.js`) rather than a generic placeholder, built directly with Pillow (no SVG renderer available/needed) since nothing else in the toolchain produces raster icons. Used for the Windows installer/exe icon (`package.json`'s `build.win.icon`), the running app's taskbar/window icon (`electron/main.js`'s `BrowserWindow` `icon` option), and the dev-server favicon (`ui/public/favicon.png`). Re-run it (`sidecar/venv/Scripts/python.exe scripts/make-icon.py`) to regenerate after any palette/branding change — one script, three consumers, always in sync.

**Not yet done**: code signing (the local build above self-signs with whatever `signtool.exe` found on this machine — not a real distribution certificate), and a genuine clean-machine test — everything above was verified on a machine that already has Python/CUDA/build tooling installed, which is exactly the condition a real first-run test needs to NOT have. Also out of scope for this pass: Mac/Linux packaging (no MPS/CPU-only story designed), auto-update, and a Terms of Service reflecting SDXL/ControlNet's RAIL++-M acceptable-use restrictions (drafted informally in THIRD_PARTY_LICENSES.md, not a real legal document).

## Status

All four zones (Main Stage, Distillation Room, Media Page, Settings) are wired up and functional, including the drag-a-bottle-onto-a-photo interaction, the pour/thread/crossfade animations, and the Essence-appears-on-the-shelf-only-after-leaving-the-room behavior.

**Style extraction/application runs a real model**: SDXL + InstantStyle (IP-Adapter) + a Tile ControlNet, not the spec's originally-suggested Flux — see [`sidecar/pipeline_manager.py`](sidecar/pipeline_manager.py) for why SDXL (the only available Flux IP-Adapter checkpoints are gated to FLUX.1-dev and their own authors say they aren't for fine-grained style transfer, whereas InstantStyle's actual style/layout block-separation is diffusers-native and proven on SDXL) and why ControlNet is needed alongside IP-Adapter (plain img2img `strength` alone let style-driven regeneration drift the target's own content/layout away — the same failure the InstantStyle authors' own follow-up paper, InstantStyle-Plus, fixes with a Tile ControlNet; verified via direct testing that content now stays intact even at `strength=0.85`). Base model and style-extraction technique stay swappable behind `sidecar/essence_store.py`'s `extract_essence` and `sidecar/generation.py`'s `apply_essence` (split out of a single `essence.py` as the file grew) per spec §2.2 — swapping in Flux later if a real InstantStyle-for-Flux combination matures is a contained change to `pipeline_manager.py`.

`strength` and `controlnet_scale` are exposed as optional `/apply` overrides (`sidecar/app.py`'s `ApplyRequest`) for further tuning without a code change — defaults (0.85 / 0.85) favor a visible style shift given ControlNet's now doing the structural heavy lifting, but how much style actually shows through varies a lot by reference image; flat/simple references show less than a texture- or color-rich photo or painting.

First run downloads ~11.5GB (SDXL base + IP-Adapter + its CLIP image encoder + Tile ControlNet + the fp16-fix VAE) into `<models-dir>/hf-cache` (see the `RASA_MODELS_DIR` note above), in the background from sidecar startup — `GET /models/status` and the in-app banner/Settings screen show progress. Extraction and application both fail fast with a 503 until it's ready, rather than hanging.

`electron/main.js`'s `sidecar:call` IPC proxy (every renderer→sidecar request goes through it, not a direct fetch — see its own comment for why) sets an explicit 40-minute timeout on its underlying `fetch`. Node's built-in `fetch` has its own default timeout that was never tuned for this app and is short enough that a real `/apply` — a first-run model download still finishing, or just a slow generation — could trip it with a raw `HeadersTimeoutError` even while the sidecar was still working correctly; 40 minutes instead gives real headroom over `pipeline_manager.get_pipeline_blocking()`'s own 1800s (30 min) first-download ceiling plus actual generation time. Caught directly against a real run, not anticipated in advance.

**Image formats**: PNG, JPEG, WebP, HEIC/HEIF (iPhone photos, via `pillow-heif`), BMP, GIF, and TIFF are all accepted, both as reference/target images and for display. HEIC and TIFF specifically have no Chromium `<img>` codec at all, so previewing them (not just processing them) routes through a new `POST /utils/preview` sidecar endpoint that decodes via Pillow and re-encodes as a displayable PNG — see `electron/main.js`'s `image:readAsDataUrl` handler. That endpoint doesn't require the style model to be loaded, so previews work even during the first-run download.

**Blend modes** (`sidecar/generation.py`'s `GenerationStrategy` classes; `blend_mode` on `/apply`, default `"none"`; the Main Stage selector also starts on Off):
- `"subject"` — on a target photo with a distinguishable subject, segments subject from background (`rembg`, `u2net` model, soft feathered mask) and runs generation twice — background at the usual strength/`controlnet_scale`, subject region at a lower, tighter strength suggested by whether a face was detected in that region (OpenCV's bundled Haar cascade, scoped to the subject's bounding box) — then composites the two through the mask. Fixes over-distorted faces from applying one global strength across the whole photo. `subject_strength`/`subject_controlnet_scale` override the suggestion; falls back to `"none"` automatically when no distinguishable subject is found. See `sidecar/segmentation.py` for the library-choice reasoning (why `rembg`+Haar cascade over SAM/`mediapipe`).
- `"depth"` — for photos without one clear subject (landscapes, group shots, product shots): estimates monocular depth (`depth-anything/Depth-Anything-V2-Small-hf`, CPU, `sidecar/depth.py`) and runs the same two-pass-plus-composite shape as `"subject"`, but blended with a continuous depth mask instead of a binary cutout — near/foreground content stays crisp, far/background content stylizes more, with a smooth rather than hard-edged transition. Same generation cost as `"subject"` (still two passes), plus one small/fast CPU depth-inference call. `depth_near_strength`/`depth_near_controlnet_scale`/`depth_far_strength`/`depth_far_controlnet_scale` override the defaults.
- `"none"` — one flat pass over the whole photo, no segmentation or depth involved.

All three share the seeded-generator-plus-`Image.composite` machinery (`generation.py`'s `_two_pass_blend`) where applicable, so multi-pass modes only ever differ by strength/`controlnet_scale`, not by grain/noise diverging between passes.

**Living parallax (Media Page, on hover)**: a finished creation isn't just a flat image — hovering it in the Media Page grid or Lightbox drives real depth-based parallax (`ui/src/components/ParallaxImage.tsx`, vanilla `three`), foreground shifting more than background as the cursor moves, continuous per-pixel displacement rather than a discrete-layer cutout trick. Needs a depth map saved alongside the creation (`media.py`'s `depth.png`), produced by `generation.py`'s `compute_depth` flag on `/apply` — **default `false`**. This is a real, separate setting from the `blend_mode` selector above: choosing `"subject"` or `"none"` does **not** disable `compute_depth`, and there is currently no UI control for it at all (a gap, not a design choice) — it was defaulted to `true` for one round of this project, then reverted after being reported as a silent, un-toggleable cost on every apply with no visible way to turn it off. With the current default, parallax simply won't be available until `compute_depth=true` is explicitly passed (a direct API call, or a future UI toggle) — an honest trade-off until it earns a real switch instead of an invisible tax. `blend_mode="depth"` still computes its own depth map on the fly regardless of this flag (`DepthGradientStrategy`'s own fallback), it just doesn't get returned/persisted for parallax unless `compute_depth` is also on.

**The Cauldron** (Distillation Room's second mode; `sidecar/essence_store.py`'s `blend_essences`, `POST /essences/blend`): distills one new Essence from a weighted mix of existing Essences and/or fresh reference photos, instead of one single reference. Both source kinds resolve to the same thing — an IP-Adapter embedding tensor, a dominant color, a thumbnail-source image — so blending is a weighted average across whichever mix was given, whether that reads as "blend two Essences" or "distill from several photos at once." The result is a completely normal Essence afterward (`technique="instantstyle-sdxl-controlnet-v1-blend"`, `version=2`) — usable, deletable, and blendable again — except it carries no `palette`/`texture`/`stroke`/`style_statistics` (no single reference image to run those analyzers against) and a new `blended_from` field recording each ingredient's name/weight/source for provenance. UI: drag existing Essence bottles into the cauldron or add photos via a new multi-select dialog (`dialog:openImages` in `electron/main.js`), adjust each ingredient's relative weight, then run the same pour/seal ritual `DistillationBottle` already used for single extraction.

**Multi-crop style purification** (`sidecar/essence_store.py`'s `_extract_purified_embedding`/`_purify_embedding`/`_sample_crops`): every fresh reference photo that becomes part of an Essence — `extract_essence`'s own reference, or a Cauldron image ingredient — is now embedded 6 times, not once: the whole image plus 5 deterministic overlapping half-scale crops of it (`NUM_PURIFICATION_CROPS`, `CROP_SEED`). Combined per-dimension as the mean across those samples, down-weighted (max 40%, `PURIFICATION_STRENGTH` — a soft mask, not a hard zero) on whichever dimensions varied most across crops. The intuition: a dimension that stays stable no matter which piece of the reference you look at is describing something true of the whole piece (texture, palette, brushwork — style); a dimension that swings depending on which crop you took is reacting to whatever specific thing happened to be in that region (content). Adapted from the content/style disentanglement idea behind MaskST (arXiv:2502.07466, ICLR 2025) — that paper masks embedding dimensions correlated with a *text* description of content, which doesn't port directly since `apply_essence` runs with no text prompt anywhere (`prompt=""`); this uses variance across crops of the same reference as the content signal instead, so it needs no text, no target image, and no training data, and runs entirely at distillation time like the rest of this module already does. Adds ~6x the (cheap, sub-second) embedding-extraction cost to `/essences/extract` and to each image ingredient in a Cauldron blend — not to `/apply`, which is unaffected.

**Apply-time content-aware masking** (`sidecar/content_mask.py`'s `mask_content_correlated`; `content_aware_masking` on `/apply`, **default off**, same reasoning as `compute_depth` above — reported as a real, silent per-apply cost with no UI control to disable it): a second, complementary purification pass, this time at apply time rather than distillation time, since only at apply time does the target photo exist. Embeds the target the same way an essence reference is embedded (`essence_store.extract_ip_adapter_embedding`), then down-weights (max 25%, gentler than distillation-time purification's 40% — this compounds on an already-purified embedding, over a noisier one-image signal) whichever dimensions of the essence's embedding correlate positively with the target's own embedding — those are the dimensions most likely restating content the target's own structure (already held in place by the Tile ControlNet) has covered, rather than contributing pure style. Same MaskST lineage as the distillation-time purification above, substituting the target's own CLIP embedding for that paper's content-text prompt. Not a reimplementation of RB-Modulation's Attention Feature Aggregation (arXiv:2405.17401) — that reformulates the denoising process itself via stochastic optimal control, a substantially bigger undertaking; this operates at the embedding level, one extra cheap CLIP encode per apply, not a change to the diffusion loop. Both passes are strictly the essence embedding used by generation.py's strategies (subject/depth/none) getting cleaner over time — segmentation.py, the GenerationStrategy classes, and the ControlNet/IP-Adapter pipeline itself are all untouched.

**Color preservation**: IP-Adapter's embedding carries the essence's own color along with its texture, which can tint the whole photo toward the essence's hue (seen directly on a real run — a strongly-colored essence turned an entire photo purple). `color_preservation` (0..1, default `1.0`) restores that fraction of the target's original color post-generation via a LAB luminance-only swap, blended continuously in the a/b chroma planes (`sidecar/color_transfer.py`) — the stylized result's luminance/texture survives throughout; at `1.0` the photo's own hue/saturation comes back fully, at `0.0` the essence's color comes through untouched, and values between are a real blend rather than an on/off toggle.

**Essence-reactive stroke texture** (`sidecar/stroke_texture.py`'s `apply_stroke_texture`; `stroke_amount` on `/apply`, **default 0 (off)** — new and not yet validated against a real photo the way `color_preservation` was): every other apply-time control (intensity, `color_preservation`, `blend_mode`) applies the same adjustment everywhere regardless of which essence was dropped — this is the first one that varies spatially with the *specific* essence's own measured stroke pattern. `style_analysis/stroke.py`'s per-cell structure-tensor field (theta/coherence, the raw data behind its four aggregate scalars) is now persisted at Distillation time (`stroke_field.npz`, loaded via `essence_store.load_stroke_field`) instead of discarded after computing them. At apply time, a small bank of Gabor kernels — the standard tool for oriented texture analysis *and* synthesis, same structure-tensor family of math `stroke.py` already runs to measure orientation in the first place — built at a handful of discrete angles is applied to the result's own luminance and composited per-pixel using whichever bin the upsampled field says that pixel's region belongs to, weighted by how confidently (coherence) that region was oriented. `cv2.getGaborKernel`'s `theta` and `stroke.py`'s own `theta` share the same convention (verified empirically: filtering noise with `getGaborKernel(theta=T)` and re-measuring it with `analyze_stroke_field` round-trips to `dominant_angle ≈ T`), so a bin's kernel reproduces stripes oriented the way the essence's own strokes were measured, with no angle conversion needed. Applied in LAB's L channel only (same convention as `color_transfer.py`), so it doesn't disturb hue/saturation. A silent no-op for any essence with no persisted stroke field — a blended (Cauldron) Essence, one saved before this existed, or one whose stroke analysis failed at Distillation time.

**Relight GIF export** (Media Page, per creation — `sidecar/relight.py`, `POST /media/{id}/gif`): a second, sibling "living image" effect to the parallax hover above — instead of the camera moving (parallax), the *light* sweeps a full circle around the subject, baked into a looping GIF (36 frames, Pillow's native animated-GIF encoding, no new dependency) so it's shareable anywhere a live WebGL hover can't go (chat, social media). Adapted from a real paper — [**"Gradient Domain Rendering"** (Wang, Gonen & Akleman, Texas A&M)](https://people.it.tamu.edu/~ergun/research/2Drendering/) — a classical (non-neural) technique for relighting flat 2D artwork from a 2D vector field (≈ the x/y channels of a normal map) plus two control images (fully-shadowed / fully-lit), diffuse shading a single per-pixel dot product; the paper itself never animates anything (it's a static relighting technique), but its own claim that even its most expensive operation is real-time-capable is exactly what makes sweeping the light over many frames fast. Two adaptations since there's no artist in the loop: the vector field is derived from the depth map already computed elsewhere in this app (`depth.py`) via its own image gradient (the standard way to get a normal-map-like field from a height field — no new model), and the two control images are generated automatically (the image itself = fully lit, a darkened copy = fully shadowed) rather than hand-painted. v1 scope is diffuse shading only — the paper's ambient occlusion and directional shadows are real, described techniques and legitimate v2 richness, not required for a visibly working effect. A full 360° light sweep makes the loop seamless for free (frame 0 and the implicit next frame are the same light angle). Computes a depth map on the fly for creations that don't already have one (most of them, since `compute_depth` defaults to `false` — see above) rather than requiring it to have been on at apply time. Every generated frame carries a small attribution credit burned into the bottom-right corner, since a GIF is exactly the kind of file that gets shared out of context, where the connection back to the paper would otherwise be lost.

**Texture overlay — a second, non-diffusion apply engine** (`sidecar/texture_overlay.py`'s `apply_texture_overlay`; `mode: "texture_overlay"` on `/apply`, alongside the existing default `mode: "restyle"`): reported directly against a real attempt — dropping a pure-texture reference (a photo of textured glass, with no real brushwork or palette to speak of) through the normal diffusion path produced a rougher, content-drifted result, because that path *regenerates* the whole image from scratch. For an essence that's really a **material** (glass, canvas, paper grain, fabric weave) rather than a painterly style, that's the wrong operation — the target needs to stay exactly as it is, just printed onto/behind the material. `mode: "texture_overlay"` skips the SDXL pipeline entirely (works even before the model finishes loading — see `app.py`'s `apply_endpoint`) and instead composites the essence's own persisted material swatch (`texture_source.png`, saved for every essence extracted since this existed) onto the target via classical bump/emboss shading, preserving the target's content with total fidelity. Reuses `relight.py`'s Gradient Domain Rendering shading directly, but *not* its depth-to-normal-field gradient scaling — that's tuned for MiDaS depth maps, which have a fairly consistent gradient-magnitude distribution scene to scene, unlike arbitrary material reference photos (a bold high-contrast pattern and a soft, subtly bumpy surface need very different absolute scaling to read as the *same* relief strength). Reported directly against a real run — a soft, low-contrast texture (a gently bumpy glass surface) came out barely visible even at full strength, measured ~4x weaker gradient signal than a higher-contrast reference at identical settings — `texture_overlay.py`'s own `_height_to_normal_field` instead auto-normalizes each texture's gradient magnitude to its own 92nd percentile (over nonzero gradients only, so a mostly-flat material with relief concentrated in a small area isn't washed out) before scaling, so relief strength reads consistently regardless of the source photo's absolute contrast. Blends between a *symmetric* darkened/brightened pair around the target's own brightness rather than relight.py's dark‥lit pair (appropriate for a GIF frame that should never exceed the source's brightness, wrong for a static overlay): a texture with no relief anywhere leaves the target completely unchanged regardless of `texture_overlay_amount`, and only actual relief pushes brightness up or down from there. `has_texture_source` on each essence (same file-existence pattern as Media's `has_gif`) tells the UI whether this mode is available for it — false for a blended (Cauldron) Essence or one saved before this existed.

**Restyle progress cue** (Main Stage): while the sidecar is generating, the photo dims under a spinner. It starts as an elapsed-seconds counter, then switches to a live readout (`Restyling… step 12/27 · 1.8s/step`, plus `pass 2/2` for two-pass blend modes) polled once a second from `GET /apply/progress` through the `sidecar:call` proxy. If the rolling-median step time exceeds 6s, a second line warns that GPU memory is full and suggests closing other GPU-heavy apps. It clears as soon as the result starts crossfading in.

**Memory plan and cached prompts** (`sidecar/pipeline_manager.py`): at load the sidecar picks a placement with `choose_memory_plan`. If at least ~9GB of VRAM is free it goes `resident` (UNet, ControlNet and VAE stay on the GPU; text and CLIP image encoders stay on CPU, and the image encoder only visits the GPU during essence extraction). Otherwise it falls back to `offload` (`enable_model_cpu_offload`), and to `cpu` with no CUDA. An OOM while going resident falls back to `offload` instead of failing the load. The plan is reported at `/health` -> `model.memory_plan`. The empty prompt and the constant negative prompt are also encoded once at load and reused, so the two text encoders no longer run on every apply. Seeded output is unchanged. Blend mode now defaults to Off (single pass, roughly half the time of the two-pass Subject mode).

**Save a creation** (Media Page, download button on hover): opens a Save-as dialog and writes the image to any folder (`image:saveDataUrl` IPC in `electron/main.js`).

Not yet built: progressive per-diffusion-step previews (the Main Stage crossfade currently animates original → final rather than several real intermediate frames), provenance metadata embedding + export (spec §3), and the future style marketplace (deferred beyond v1 per spec §7).

### Verifying it runs

`npm run dev` opens the real window. For headless/agent verification (this shell sets `ELECTRON_RUN_AS_NODE=1`, which breaks a direct Electron launch — unset it):

```
npm run dev:ui                                              # start Vite first, separately
env -u ELECTRON_RUN_AS_NODE node scripts/verify-launch.mjs   # launch + screenshot the current screen
env -u ELECTRON_RUN_AS_NODE node scripts/verify-flow.mjs <ref-image> <target-image>   # full extract -> apply -> media flow, screenshot per step
```

Both need `playwright-core` (`npm install --no-save playwright-core`) and screenshot to `.tmp-shots/`.
